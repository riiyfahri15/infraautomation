## Intentional Bugs Planted for the Competition

There are **8 deliberate bugs** across the application code and CI/CD pipeline.
Students must find and fix all of them as part of **Task 2** and **Task 4**.

---

### Bug 1 — Wrong env var name for SQS queue URL

| | |
|---|---|
| **File** | `api/sqs.py` — line 10 |
| **Bug** | `os.getenv("SQS_URL", "")` |
| **Fix** | Change `"SQS_URL"` → `"SQS_QUEUE_URL"` |
| **Effect** | `QUEUE_URL` is always empty string; SQS events are silently skipped even when the env var `SQS_QUEUE_URL` is properly set in the ECS task definition |
| **Difficulty** | ⭐⭐ Medium — requires comparing env var name in code vs what's set in ECS / `.env` |

---

### Bug 2 — Wrong SSL mode for RDS connection

| | |
|---|---|
| **File** | `api/db.py` — line 29 |
| **Bug** | `sslmode="disable"` |
| **Fix** | Change to `sslmode="require"` |
| **Effect** | API cannot connect to RDS PostgreSQL in production. AWS RDS enforces SSL by default (`rds.force_ssl=1`). Works fine in local dev (PostgreSQL container doesn't enforce SSL) so the bug only manifests when deployed. |
| **Difficulty** | ⭐⭐⭐ Hard — works locally, fails silently in production. The docstring in the same file even hints at the correct value. |

---

### Bug 3 — Wrong env var name for metrics port

| | |
|---|---|
| **File** | `api/app.py` — line 80 |
| **Bug** | `os.getenv("METRIC_PORT", 9100)` |
| **Fix** | Change `"METRIC_PORT"` → `"METRICS_PORT"` |
| **Effect** | The metrics Flask server always starts on port `9100` (the default) regardless of `METRICS_PORT` env var. Since both the bug default and the intended value are `9100`, the server actually starts — but if a custom port is set via env var it will be ignored. More importantly, Prometheus scraping may fail if the task definition sets a different `METRICS_PORT`. Also, `docker-compose.yml` sets `METRICS_PORT=9100` which is also ignored. |
| **Difficulty** | ⭐ Easy — straightforward typo; visible by searching `METRICS_PORT` across files |

---

### Bug 4 — Missing `conn.commit()` in DELETE endpoint

| | |
|---|---|
| **File** | `api/routes/users.py` — `delete_user()` function |
| **Bug** | `conn.commit()` is absent after the `DELETE FROM users` statement |
| **Fix** | Add `conn.commit()` before `publish_event(...)` inside `delete_user()` |
| **Effect** | `DELETE /api/users/:id` returns `204 No Content` (success), but the transaction is never committed. On the next request, `psycopg2` auto-rolls back the open transaction, so the deleted user reappears. |
| **Difficulty** | ⭐⭐⭐ Hard — the endpoint appears to work (returns 204), but the data is not actually deleted. Requires testing with a GET after DELETE. |

### Bug 5 — Wrong env var name for API URL in frontend

| | |
|---|---|
| **File** | `frontend/app.py` — line 9 |
| **Bug** | `API_URL = os.getenv("BACKEND_URL", "")` |
| **Fix** | Change `"BACKEND_URL"` → `"API_URL"` |
| **Effect** | `API_URL` is always empty string. The template renders with `api_url=""`, so all browser API calls go to an empty base URL (i.e., relative path `/api/users` from the frontend container — not the actual API service). The page loads but shows no data. |
| **Difficulty** | ⭐⭐ Medium — the page loads without JavaScript errors, data just doesn't appear. |

### Bug 6 — Wrong Python version in CI pipeline

| | |
|---|---|
| **File** | `.github/workflows/lks-cicd.yml` — `install` job, line 27 |
| **Bug** | `python-version: "3.11"` |
| **Fix** | Change to `python-version: "3.13"` (matching all Dockerfiles) |
| **Effect** | The `install` job runs import tests on Python 3.11 while the Docker images use Python 3.13. Any syntax or import that's 3.13-specific will pass locally in Docker but fail in the CI test step. Conversely, a deprecation in 3.11 won't be caught. Also makes the CI environment inconsistent with production. |
| **Difficulty** | ⭐ Easy — visible by comparing workflow python-version vs Dockerfile `FROM python:3.13-slim` |

### Bug 7 — ECR registry for monitoring images uses wrong secret

| | |
|---|---|
| **File** | `.github/workflows/lks-cicd.yml` — global `env` block, line 12 |
| **Bug** | `ECR_REGISTRY_MONITORING: ${{ secrets.ECR_REGISTRY }}` |
| **Fix** | Change to `${{ secrets.ECR_REGISTRY_MONITORING }}` |
| **Effect** | Monitoring images (Prometheus, Grafana, Loki, Alertmanager) are pushed to the **us-east-1** ECR registry instead of **us-west-2**. The `build_and_push_ecr_monitoring` job will push successfully (no error) but to the wrong registry — the monitoring ECS cluster in us-west-2 will fail to pull the images. |
| **Difficulty** | ⭐⭐ Medium — no build error, failure only visible when the monitoring ECS tasks fail to start. Requires reading the env block carefully. |

---

### Bug 8 — `upload_to_s3` job runs before images are built

| | |
|---|---|
| **File** | `.github/workflows/lks-cicd.yml` — `upload_to_s3` job |
| **Bug** | `needs: install` |
| **Fix** | Change to `needs: build_and_push_ecr` |
| **Effect** | The S3 metadata upload job starts immediately after the `install` job, in parallel with the ECR build job. The metadata JSON includes the image URIs — but since the images haven't been pushed yet at this point, the metadata may be misleading or the deployment references a tag that doesn't exist yet. |
| **Difficulty** | ⭐⭐ Medium — requires understanding GitHub Actions job dependency graph |
